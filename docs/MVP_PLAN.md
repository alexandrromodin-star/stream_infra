# Stream — план формирования и проверки MVP

**Версия:** 0.1, рабочее предложение  
**Дата:** 2026-10-25  
**Цель документа:** определить следующий порядок работ и снизить риск начать строить приложение до проверки главных ограничений.

## 1. Предлагаемая граница MVP

Для первой версии не строить универсальный редактор фильмов. Подготовить одну короткую сцену и проверить полный путь от сцены до записи в OBS.

Предлагаемые ограничения первого образца:

- один короткий фрагмент и один выбранный персонаж;
- выбирать сцену с хорошо видимым лицом, желательно без частых перекрытий, сильных поворотов и резких склеек;
- сцена воспроизводится непрерывно по исходному таймингу;
- лицо актёра поступает с веб-камеры в реальном времени;
- голос персонажа пользователя должен заменять оригинальную реплику; остальные голоса/музыка/эффекты сохраняются насколько позволяет подготовка;
- OBS принимает итоговые аудио и видео и выполняет запись;
- подготовка одной сцены на первом прототипе может выполняться вручную в бесплатных open-source программах.

Это временная граница для технического прототипа, а не окончательное ограничение продукта.

## 2. Принцип подготовки видео

Не считать, что видео обязательно всегда обрабатывать вручную. Самый простой и контролируемый MVP — **гибридный процесс**: программа автоматически делает повторяемую тяжёлую работу (декодирование, воспроизведение, захват камеры, композитинг), а человек один раз настраивает сцену (выбирает персонажа и поправляет маску/таймкоды).

Полная автоматизация выбора правильного лица в каждом кадре, поведения на монтаже, перекрытий и синхронизации с репликами — отдельный этап после того, как один гибридный шаблон заработает.

## 3. Пошаговый план

### Шаг 1. Утвердить пример сцены и критерии

Кандидат на первую сцену уже подготовлен: `D:\Stream\scenes\WFWS - small part.mp4`. Сначала проверить его длительность, разрешение, FPS, число планов/склеек, видимость лица и пересечения реплик. Если клип слишком сложный для первого прототипа, взять из него более простой непрерывный план или заменить тестовой сценой. Записать таймкоды реплик и участки, где звучит речь целевого персонажа.

На этом шаге не писать приложение. Создать один паспорт тестовой сцены и сохранить исходник отдельно от Git.

### Шаг 2. Проверить подготовку звука вручную

1. В Ultimate Vocal Remover GUI (UVR) получить отдельные vocal и instrumental stems.
2. Загрузить исходный звук и stems в Audacity, выровнять по началу и прослушать, что сохранилось.
3. В vocal stem отметить временные области целевого персонажа и убрать/приглушить только их; реплики остальных персонажей оставить.
4. Смешать изменённый vocal stem с instrumental stem и проверить рядом с исходным видео.

**Ограничение:** стандартное отделение «вокал/инструментал» не означает отделение одного актёра от другого. Если голоса перекрываются, либо модель оставляет артефакты/теряет эффекты, для первой сцены выбрать другой фрагмент. Спектральный редактор Audacity полезен для точечных дефектов, но не следует рассчитывать, что он чисто удалит сложную речь из смешанного киноаудио.

### Шаг 3. Подготовить маску и трек лица персонажа

В Kdenlive открыть исходный фрагмент. Сначала попробовать встроенный Motion Tracker для получения ключевых кадров движения лица/области. Затем создать маску/матт целевого лица через Rotoscoping и вручную поправить ключевые кадры на важных позах и склейках.

Kdenlive также содержит Object Mask на базе SAM2. Это можно сравнить как полуавтоматический вариант, но он требует предварительной настройки и установки моделей; поэтому не делать его обязательным для первого теста.

На выходе сохранить не только красиво обработанное видео, а данные, пригодные приложению: таймкоды, границы кадров/планов, координаты/маску, исходное соотношение сторон и тестовый рендер. Уточнить формат этих данных после пробы экспорта Kdenlive.

### Шаг 4. Проверить живую подстановку лица

Начать с простого композитинга: приложение берёт кадр фильма, захватывает лицо/мимику с камеры, масштабирует и совмещает слой с подготовленной маской и ключевыми кадрами. Это позволит проверить самый простой вариант без собственной модели face swap.

Если результат выглядит как плоская наклейка, сравнить второй вариант — готовую модель live face swap или переноса мимики. FaceFusion можно использовать как benchmark для производительности веб-камеры и передачи в OBS, но его webcam-режим сам по себе не решает задачу «источник — камера, целевое лицо — персонаж внутри фильмового кадра».

Зафиксировать текущую отправную точку: GTX 1060 с 3 ГБ VRAM. Замерить FPS, задержку, загрузку VRAM и нагрев для каждого кандидата. По этим результатам решать, какое оборудование покупать.

### Шаг 5. Собрать минимальный runtime

Минимальный исполняемый поток:

```text
шаблон сцены -> кадры исходного видео -> трек/маска -> live-композитинг с веб-камерой
             -> финальный видеокадр -> OBS

изменённый фон сцены + живой микрофон актёра -> синхронный микс -> OBS
```

Первый UI может содержать только выбор шаблона, камеры и микрофона, предварительный просмотр и кнопки «Запуск / Стоп». Монтаж, сложная настройка масок, каталог сцен и управление всей OBS-сессией в MVP не входят.

### Шаг 6. Проверить сквозной сценарий в OBS

Подключить Stream к OBS самым простым стабильным способом, доступным прототипу. Сначала проверить захват окна/видеопотока и звука приложения, затем решить, нужен ли виртуальный видеовыход, отдельное аудиоустройство или управление OBS через WebSocket.

OBS имеет захват звука отдельного приложения на Windows 10 версии 2004+ и Windows 11. Его можно попробовать для приёма звука приложения без добавления виртуального аудиокабеля. OBS WebSocket нужен только если Stream должен запускать запись, менять сцену или показывать состояние OBS.

### Шаг 7. Зафиксировать критерии приёмки

Перед разработкой полноценного UI согласовать измеримые пороги:

- сцена стартует с исходного начала и завершается без изменения FPS/длины;
- целевая речь оригинального персонажа не мешает голосу пользователя;
- речь других персонажей и фон остаются приемлемыми на слух;
- лицо не «съезжает» с персонажа на обычных движениях тестовой сцены;
- воспроизведение не даёт заметных пропусков кадров;
- рассинхрон аудио/видео и задержка камеры измерены и приемлемы для актёрского дубля;
- OBS записывает один полный дубль без ручной перенастройки маршрутизации.

Числовые пороги FPS, задержки, рассинхрона и времени подготовки одной сцены пока не утверждены; измерить их на прототипе и согласовать до фиксации аппаратных требований.

### Шаг 8. По результатам прототипа зафиксировать техтребования

Создать финальный краткий PRD, архитектурную схему, формат шаблона сцены, список сторонних зависимостей и лицензий, структуру задач разработки и инструкцию запуска. Только после этого начинать полноценное приложение.

## 4. Инструменты для максимально простого ручного старта

| Задача | Инструмент | Как использовать в MVP |
|---|---|---|
| Обрезать клип, посмотреть кадры, подготовить маски и keyframes | Kdenlive | Один монтажный проект на сцену; Motion Tracker как подсказка; Rotoscoping для ручной коррекции маски. |
| Полуавтоматически выделить область | Kdenlive Object Mask (SAM2) | Необязательный эксперимент; требует настройки и установки моделей. |
| Разделить песню/вокал и фон | UVR GUI | Создать вокальный и инструментальный stems; проверить лицензии используемой модели. |
| Удалить целевые реплики из vocal stem и свести звук | Audacity | Метки времени, редактирование/приглушение областей, прослушивание и экспорт микса. |
| Управлять выходной записью | OBS Studio | Принимать/записывать итоговый поток; автоматизацию добавить только при необходимости. |

## 5. Открытые вопросы перед фиксацией MVP

1. Какой ориентир важнее: правдоподобное лицо пользователя или максимально точная мимика/актёрское исполнение с камеры?
2. Готов ли MVP ограничить первую сцену крупным планом без перекрытий и длинных поворотов?
3. Для первой сцены допустимо ли, что подготовка аудио требует ручной проверки и выбора фрагмента без пересекающихся реплик?
4. Нужно ли слышать пользователю оригинальное видео локально в наушниках во время игры, при том что его голос/фон уже идут в OBS?
5. Предпочтительное целевое качество и FPS: оставить исходный формат сцены или начать с 720p/30 для доступного теста на GTX 1060?
